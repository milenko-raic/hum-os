# 00 · Notice to Navigation

HUM-OS is a personal behavior navigation environment for interrupting automatic patterns, routing difficult moments, choosing bounded next actions and preserving evidence about what actually changes behavior.

It is designed to answer a small set of questions before an impulse becomes an automatic action:

- What is happening right now?
- What behavior is being triggered?
- How strong is the signal?
- What boundary has the user already chosen?
- What is the smallest useful intervention?
- What support surface is appropriate?
- What evidence should be recorded?
- What observable condition closes the moment?

The governing flow is intentionally simple:

```text
SIGNAL → INTERRUPT → ROUTE → ACTION → EVIDENCE → RELEASE → LOG
```

HUM-OS converts an automatic behavioral moment into a bounded, observable and reviewable decision.

It does not attempt to govern the human.

It governs the **navigation surface between impulse and action**.

# 02 · Purpose

HUM-OS is not a motivation dashboard.

It is an operational decision surface for moments in which behavior is likely to become automatic.

Its purpose is to make the relationship between **trigger, impulse, action, support and evidence** visible enough to interrupt.

## Core questions

| Signal | Question | Required outcome |
|---|---|---|
| Intent | What is the user trying to change? | Explicit charter |
| Trigger | What initiated the moment? | Named behavioral cue |
| Intensity | How strong is the pull? | Current signal level |
| Boundary | What action is allowed? | Bounded behavioral objective |
| Route | What should happen next? | One defensible next action |
| Support | What resource reduces the load? | Appropriate support surface |
| Evidence | What happened? | Recordable observation |
| Release | When is the moment closed? | Observable closure condition |

A strong interface does not produce more text.

It produces a better decision.

# 05 · Protocol Registry

## IN-01 · Interrupt

**Trigger:** an automatic behavioral sequence is beginning.  
**Objective:** create a decision gap between impulse and action.  
**Required output:** a short interruption that changes the state before the behavior executes.

## RT-02 · Route

**Trigger:** a behavioral signal has been identified.  
**Objective:** match current context to the smallest useful next action.  
**Required output:** one route with a clear purpose, bounded duration and release condition.

## BR-03 · Bridge

**Trigger:** the user needs a transition rather than a hard stop.  
**Objective:** preserve the useful part of the context while changing the behavioral script.  
**Required output:** a practical bridge from current state to intended behavior.

## GT-04 · Gate

**Trigger:** access, proximity or automatic execution is the main risk.  
**Objective:** make the unwanted action harder to execute immediately.  
**Required output:** a visible change in the control surface.

## CL-05 · Calm

**Trigger:** intensity is elevated and cognitive routing is likely to degrade.  
**Objective:** reduce immediate physiological or cognitive load before further decisions.  
**Required output:** a short calming passage followed by reassessment.

## SG-06 · Signal

**Trigger:** human contact is more useful than additional self-navigation.  
**Objective:** create a bridge to another person.  
**Required output:** an explicit support signal the user may send.

## EV-07 · Evidence Check

**Trigger:** assumptions are being treated as conclusions.  
**Objective:** separate evidence states.

| State | Meaning |
|---|---|
| Observed | Directly noticed or recorded |
| Inferred | Reasonable interpretation of observed evidence |
| Unverified | Claimed or assumed but not confirmed |
| Contradicted | Evidence exists against the claim |

## EX-08 · Release Review

**Trigger:** the immediate behavioral moment has changed state.  
**Objective:** decide whether to close, continue, escalate to support or record a lapse/re-entry event.  
**Required output:** explicit closure status and supporting evidence.

# 06 · Intervention Depth Classification

| Class | Designation | Scope |
|---|---|---|
| I | Notice | Awareness, labeling or simple observation |
| II | Interrupt | Small immediate change to break automaticity |
| III | Structured Route | Trigger-specific action with explicit boundary |
| IV | Supported Passage | Human, environmental or expert support required |
| V | Safety Hold | Runtime stops normal routing and directs toward appropriate professional or emergency support |

An intervention must not silently increase its depth.

If the runtime crosses into medical withdrawal, medication changes, acute mental or physical health risk or another safety-critical state, HUM-OS should leave ordinary habit routing and enter the appropriate safety boundary.

# 09 · Acceptance Test

A feature is not complete because it renders.

A route is not complete because text was generated.

A streak is not complete because a timer is running.

A behavioral intervention is not complete because the user pressed a button.

Completion requires observable evidence that the intended runtime state has changed.

## Minimum acceptance conditions

- active behavior is identified,
- charter mode is explicit,
- trigger or condition is known,
- intensity is visible when relevant,
- next action is finite,
- support surface is appropriate,
- user authority remains intact,
- evidence can be recorded,
- release condition is observable,
- result remains understandable outside the interface.

**Reality remains the acceptance test.**

# 14 · Engineering Principles

## Prefer explicit over implied

If intent matters, write it.  
If a trigger matters, name it.  
If a boundary matters, define it.  
If evidence matters, classify it.  
If closure matters, record it.

## Prefer finite over permanent

Every intervention should have a start, a purpose, a bounded action, an observable result and a release condition.

## Prefer interruption over persuasion

The system does not need to argue with the user.

It needs to create enough space for a deliberate choice.

## Prefer evidence over self-judgment

A lapse is an event.

It is not a verdict.

The useful questions are what triggered it, what happened before it, what intervention was available, what changed intensity and what should change next time.

## Prefer local-first over unnecessary collection

Where possible:

- store personal behavioral data locally,
- avoid requiring an account,
- avoid collecting information the runtime does not need,
- make data boundaries visible,
- allow the user to retain conceptual ownership of their own evidence.

## Prefer boring infrastructure over decorative complexity

The system should remain understandable when the original author is absent, the interface changes, the browser is offline, a behavior changes, a feature is removed or a result must be reviewed.

# 15 · Failure Conditions

| Condition | Response |
|---|---|
| No active charter | Ask the user to define intent |
| Trigger unknown | Observe before routing |
| Route has no bounded action | Reject route |
| Action expands silently | Re-route |
| Intensity becomes safety-critical | Escalate support boundary |
| Evidence cannot be classified | Perform EV-07 |
| User authority is obscured | Stop advisory escalation |
| Lapse deletes all useful history | Preserve evidence and re-entry |
| Runtime loops without closure | Perform EX-08 |
| Interface claims success without evidence | Reject completion |
| Medical-risk context is treated like an ordinary habit | Enter Safety Hold |

# Safety Boundary

HUM-OS is a behavioral navigation and evidence interface.

It is not a substitute for medical care, diagnosis, treatment, crisis support or professional withdrawal planning.

Some substance-use patterns, medication changes, severe withdrawal states, acute mental-health conditions or physical-health risks require professional guidance.

In immediate danger, appropriate emergency services take priority over the runtime.

---

# Privacy Position

The current HUM-OS prototype is designed around a local-first model.

Where implemented as a standalone browser application:

- behavioral state is stored locally in the browser,
- no account is required,
- the user is responsible for what they intentionally enter,
- advisory output does not imply engagement by any external authority,
- personal behavioral evidence should not be transmitted unless the user deliberately chooses a support or external workflow.
